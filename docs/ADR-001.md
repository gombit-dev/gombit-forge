# ADR-001 — Forge Stable Identity, File Ownership, and Extension ABI

**Status:** Proposed — intended to be locked before F0
**Product:** Gombit Forge
**Scope:** Project identity model, generated-code ownership, user-code ownership, extension ABI, spec mutation compatibility
**Decision owners:** Gombit Forge architecture
**Depends on:** Gombit machine-generation contract
**Related future ADRs:** Migration Intent & Safety Manifest; Local Runtime Toolchain; ProjectSpec Serialization

---

## 1. Context

Gombit Forge is a local-first visual application builder that compiles a declarative `ProjectSpec` into an ordinary Gombit application.

Forge must support two goals that are naturally in tension:

1. Forge must be able to repeatedly regenerate substantial parts of an application from the visual specification.
2. Developers must be able to add limited custom behavior without permanently ejecting the project from Forge.

A pure generator solves the first problem but creates an eject cliff:

```text
no-code
   ↓
need one custom behavior
   ↓
export
   ↓
Forge can never manage the project again
```

Allowing arbitrary source edits inside generated files creates the opposite problem: Forge would need bidirectional reconciliation between visual state and arbitrary user modifications.

That is explicitly rejected.

The intended model is therefore:

```text
                    ProjectSpec
                         │
                         ▼
                  Forge Compiler
                         │
          ┌──────────────┴──────────────┐
          │                             │
          ▼                             ▼
 compiler-owned code             stable extension ABI
                                        │
                                        ▼
                                  user-owned code
```

Forge regenerates only the compiler-owned side.

User code exists only behind deliberately narrow extension points.

This means Forge does **not** eliminate reconciliation entirely. It narrows reconciliation to one controlled problem:

> Changes to `ProjectSpec` must preserve, or explicitly break, the stable API against which extension code compiles.

That contract is the subject of this ADR.

---

# 2. Decision summary

Forge adopts the following rules.

### D1 — Every semantic object has a permanent stable ID

Resources, fields, relationships, pages, actions, hooks, and other addressable spec entities receive immutable IDs at creation.

Example:

```json
{
  "id": "res_01K2M...",
  "name": "customer",
  "label": "Customer"
}
```

A field:

```json
{
  "id": "fld_01K2N...",
  "name": "email",
  "label": "Email address"
}
```

The ID represents identity.

Names and labels represent presentation or mapping.

---

### D2 — Human labels, database names, and code symbols are separate concepts

A Forge field has at least:

```text
stable identity
human label
database name
generated code symbol
```

For example:

```text
ID           fld_01K2N...
Label        Contact email
DB column    contact_email
Code symbol  Email
```

These may evolve independently according to explicit rules.

---

### D3 — Generated code symbols freeze at creation

The generated code identifier assigned when an entity is created does **not** automatically follow later visual renames.

Example:

Initial field:

```text
Label:       Email
DB column:   email
Code symbol: Email
```

User later performs a normal Forge rename:

```text
Label:       Contact email
DB column:   contact_email
Code symbol: Email
```

The extension ABI remains stable.

A hook written before the rename continues compiling.

---

### D4 — Changing a code symbol is a separate explicit breaking refactor

Forge never silently performs:

```text
Email → ContactEmail
```

merely because the visual field was renamed.

A user may explicitly request:

> Rename generated code identifier

That operation is classified as a **breaking source refactor**.

Forge must analyze extensions before committing it.

---

### D5 — Extension code never lives inside compiler-owned directories

Compiler-owned and user-owned files are structurally separated.

Forge must never require marker-based partial rewriting of user code.

---

### D6 — Extensions bind to a narrow generated contract, not raw persistence internals

Extension APIs must not expose raw compiler implementation details unnecessarily.

In particular, hooks should not depend directly on arbitrary generated GORM persistence machinery where a narrower stable contract can serve the same purpose.

---

### D7 — Forge validates extension compatibility before accepting a breaking spec transition

Forge must compile-check extension code against the candidate generated contract before committing a spec mutation that can alter the extension ABI.

A known-incompatible transition is rejected before it becomes the current project state.

---

### D8 — Forge never rewrites user extension implementations

Forge may:

* generate extension interfaces;
* generate empty extension directories initially;
* generate a user file once when the user explicitly creates a hook;
* report compiler errors;
* offer migration guidance.

Forge must not subsequently rewrite user implementation code.

---

### D9 — Export preserves the distinction but removes Forge ownership semantics

After export, all source belongs to the user.

Generated-file banners remain useful documentation, but Forge has no authority over the repository once the user elects to leave managed mode.

---

# 3. Identity model

## 3.1 Resource identity

Example resource:

```json
{
  "id": "res_01K2M6RXQ8CJ...",
  "label": "Customer",
  "code_name": "Customer",
  "storage_name": "customers"
}
```

Semantics:

| Property       | Purpose                     |                            Mutable |
| -------------- | --------------------------- | ---------------------------------: |
| `id`           | Permanent semantic identity |                                 No |
| `label`        | UI/display name             |                                Yes |
| `code_name`    | Generated Go/TS API symbol  | Only by explicit breaking refactor |
| `storage_name` | DB/table mapping            |      Yes, through migration intent |

---

## 3.2 Field identity

Example:

```json
{
  "id": "fld_01K2M7...",
  "resource_id": "res_01K2M6...",
  "label": "Email",
  "code_name": "Email",
  "storage_name": "email",
  "type": "string"
}
```

Normal user rename:

```text
"Email"
      ↓
"Contact email"
```

may result in:

```json
{
  "id": "fld_01K2M7...",
  "label": "Contact email",
  "code_name": "Email",
  "storage_name": "contact_email"
}
```

Identity did not change.

The migration layer can therefore understand:

> `email` and `contact_email` represent the same field.

It must not infer:

> delete `email`, create unrelated `contact_email`.

---

# 4. Why code symbols freeze

A user extension may compile against a generated API.

If visual labels automatically renamed symbols, then:

```go
customer.Email
```

could silently become:

```go
customer.ContactEmail
```

and break user code merely because someone changed wording in the editor.

That would make low-code extensions fragile enough to recreate the eject cliff.

Therefore:

> **Presentation changes are cheap. Source API changes are explicit.**

Forge optimizes for long-lived extension compatibility, not automatic prettification of exported code.

---

# 5. Explicit code normalization

Frozen symbols create a known wart.

Suppose:

```text
Customer
```

is renamed in the product to:

```text
Client
```

After many months, exported source may still contain:

```go
type Customer struct {
    ...
}
```

even though Forge displays “Client.”

That is intentional during managed operation because ABI stability is more important.

Forge should eventually provide an explicit operation:

```text
Normalize code identifiers
```

or:

```text
Refactor generated symbols to current labels
```

This is a deliberately breaking operation.

Forge must:

1. calculate all symbol changes;
2. find affected extension contracts;
3. regenerate into a candidate workspace;
4. compile the full project;
5. report exact extension failures;
6. require explicit approval;
7. commit the change only when compatibility is restored.

This operation must never run automatically during export.

# 6. File ownership model

## 6.1 Proposed project layout

```text
my-app/
├── cmd/
│   └── server/
│       └── main.go
│
├── internal/
│   ├── forge_generated/
│   │   ├── customer/
│   │   │   ├── model.go
│   │   │   ├── contract.go
│   │   │   ├── handler.go
│   │   │   ├── routes.go
│   │   │   └── extension_api.go
│   │   │
│   │   └── project/
│   │       ├── ...
│   │
│   └── extensions/
│       ├── customer/
│       │   └── hooks.go
│       └── project/
│           └── hooks.go
│
├── frontend/
│   ├── src/
│   │   ├── forge_generated/
│   │   └── extensions/
│   │
│   └── ...
│
├── database/
│   └── migrations/
│
├── forge.json
├── gombit.yaml
└── go.mod
```

---

## 6.2 `forge_generated/`

Everything beneath:

```text
internal/forge_generated/
```

is owned completely by Forge.

Files contain a banner such as:

```go
// Code generated by Gombit Forge. DO NOT EDIT.
```

Forge may:

* recreate;
* delete;
* move;
* reorder;
* completely replace

these files when compiling a new spec revision.

Users must assume edits beneath this boundary will be lost.

---

## 6.3 `extensions/`

Everything beneath:

```text
internal/extensions/
```

belongs to the user.

Forge must never rewrite an existing implementation file.

Forge may inspect or compile these files because compatibility checking is part of project validation.

---

# 7. Extension ABI

## 7.1 Core rule

Extensions compile against an intentionally small generated API.

They do not reach arbitrarily into generated implementation internals.

A first-cut lifecycle could include:

```text
BeforeCreate
AfterCreate

BeforeUpdate
AfterUpdate

BeforeDelete
AfterDelete
```

Do not begin with dozens of extension points.

The extension surface should grow only in response to demonstrated needs.

---

# 8. Generated extension contract

For a resource whose frozen code name is:

```text
Customer
```

Forge may generate:

```go
package customer

import "context"

type Hooks interface {
    BeforeCreate(
        context.Context,
        *CreateContext,
    ) error

    AfterCreate(
        context.Context,
        CustomerView,
    ) error
}
```

However, extension-visible types require stronger stability rules than arbitrary generated transport or GORM types.

---

# 9. Extension-visible resource representation

## 9.1 Do not expose the mutable GORM model directly by default

Rejected default:

```go
AfterCreate(ctx context.Context, customer *Customer) error
```

if `Customer` is also the compiler's raw persistence structure.

That binds extension code to:

* persistence representation;
* ORM tags;
* schema mechanics;
* generated-field layout;
* implementation refactors.

Instead, Forge should generate a stable extension-facing representation.

Conceptually:

```go
type CustomerView interface {
    ID() CustomerID
    Email() string
}
```

or another narrow generated value/accessor API.

Exact Go ergonomics remain an implementation detail to validate in F0.

The architectural requirement is:

> Extension-visible APIs are deliberately designed contracts, not accidental exposure of generated implementation structs.

---

# 10. Stable field access

A hook should depend on a frozen source-level accessor.

Example at field creation:

```text
stable field ID: fld_abc
code name:       Email
```

Forge generates:

```go
type CustomerView interface {
    Email() string
}
```

Later the UI label changes:

```text
Email
  ↓
Contact email
```

and the storage column becomes:

```text
email
  ↓
contact_email
```

The generated extension-facing contract remains:

```go
Email() string
```

because the source identifier is frozen.

Therefore user code remains:

```go
func (h Hooks) AfterCreate(
    ctx context.Context,
    customer customer.CustomerView,
) error {
    sendWelcome(customer.Email())
    return nil
}
```

with no change required.

---

# 11. Why not stable-ID accessors in normal source code

An alternative would expose:

```go
customer.Field("fld_01K2M...")
```

This would be maximally rename-safe but produces poor Go ergonomics and undermines the promise that exported applications remain ordinary maintainable software.

Therefore stable IDs are compiler metadata, not the ordinary programming interface.

Frozen source identifiers are the human-readable ABI manifestation of stable identity.

---

# 12. Hook registration

No reflection-based hook discovery.

Generated wiring explicitly registers extension implementations.

Example:

```go
extensions.RegisterCustomerHooks(
    customerhooks.New(),
)
```

or an equivalent typed registration mechanism.

The exact API may change during F0.

Requirements:

* compile-time type checking;
* explicit registration;
* deterministic behavior;
* no filesystem/runtime magic;
* no request-time reflection discovery.

---

# 13. Creating a hook

When a user enables:

```text
Customer → Hooks → After Create
```

Forge does two things.

### Compiler-owned change

Regenerates the contract/wiring required to invoke the extension.

### User-owned change

If no implementation file exists, Forge may create:

```text
internal/extensions/customer/hooks.go
```

exactly once.

Example:

```go
package customer

import (
    "context"

    generated "example/internal/forge_generated/customer"
)

type Hooks struct{}

func (Hooks) AfterCreate(
    ctx context.Context,
    value generated.CustomerView,
) error {
    // TODO: add custom behavior.
    return nil
}
```

Once created, this file is permanently user-owned.

If it already exists, Forge must not edit it.

---

# 14. Candidate-spec validation

Forge must not mutate the live project directly.

A spec change follows:

```text
current ProjectSpec
        │
        ▼
candidate ProjectSpec
        │
        ▼
candidate generation workspace
        │
        ├── generate compiler-owned files
        ├── preserve/copy user extensions
        ├── validate relationships
        ├── validate migration intent
        └── compile/typecheck
                │
        ┌───────┴────────┐
        │                │
      valid            invalid
        │                │
        ▼                ▼
 commit revision      reject change
```

This makes extension compatibility a **spec acceptance property**, not something discovered accidentally later.

---

# 15. Compatibility classes

Forge classifies spec changes.

## Class A — ABI-neutral

Examples:

* label change;
* help-text change;
* field display ordering;
* navigation change;
* DB-column rename while code symbol remains frozen;
* adding an unrelated field;
* adding a page.

No extension intervention should normally be necessary.

---

## Class B — ABI-additive

Examples:

* adding a new extension-visible accessor;
* adding a resource;
* enabling a new optional hook point.

Existing extensions should continue compiling.

---

## Class C — ABI-breaking

Examples:

* field type change visible through an accessor;
* field removal used by extensions;
* resource removal with hooks;
* explicit generated code-symbol rename;
* incompatible relationship type change.

Forge must perform candidate compilation.

If user code fails, the transition is blocked.

---

# 16. Error experience

A rejected visual change should not merely show:

```text
go build failed
```

Forge should translate known compatibility failures into domain language.

Example:

> **Cannot remove “Email”.**
>
> `internal/extensions/customer/hooks.go` uses the generated accessor `Customer.Email()`.
>
> Remove or update that extension before deleting this field.

For an explicit symbol refactor:

> **Renaming code symbol `Email` → `ContactEmail` is a breaking source change.**
>
> 2 extension references must be updated before this refactor can be committed.

Raw compiler diagnostics should remain available under:

```text
Show build details
```

---

# 17. True deletion semantics

Deleting an entity is different from relabeling or renaming it.

A field deletion means its stable identity disappears from the active spec.

Before deletion Forge checks:

```text
relationships
pages
filters
permissions
admin configuration
hooks
extension ABI
migration safety
```

Any hard dependency must either:

* be removed in the same transaction; or
* cause the candidate spec to be rejected.

---

# 18. Resource deletion

Forge must never allow:

```text
Delete Customer
```

to create a revision where:

```text
Project.Customer relationship
```

still exists.

Likewise, if:

```text
internal/extensions/customer/hooks.go
```

contains a registered implementation, resource deletion requires an explicit extension decision.

Possible UI:

> Customer has custom extension code.
>
> Deleting this resource will remove the generated extension contract, leaving `internal/extensions/customer/` orphaned.
>
> Forge will **not delete your custom files**.

Options:

```text
Cancel
Delete resource and retain orphaned extension files
```

Forge never deletes the user-owned directory automatically.

---

# 19. Orphaned extension code

When a resource is intentionally deleted, its user extension may remain on disk.

Forge records it as orphaned.

Example:

```text
internal/extensions/customer/
```

The UI may surface:

> Extension files exist for a deleted resource.

Forge does not compile orphaned extensions into the application.

This preserves user work while keeping the active application valid.

---

# 20. Mutation scenario 1 — rename a field used by a hook

Initial state:

```text
Resource: Customer
Field:
  ID:        fld_A
  Label:     Email
  DB name:   email
  Code name: Email
```

Hook:

```go
func (Hooks) AfterCreate(
    ctx context.Context,
    c generated.CustomerView,
) error {
    return sendWelcome(c.Email())
}
```

User changes visual field name to:

```text
Contact email
```

Desired new state:

```text
ID:        fld_A
Label:     Contact email
DB name:   contact_email
Code name: Email
```

Effects:

```text
UI label        changes
DB name         changes
migration       rename_column
code accessor   unchanged
hook            unchanged
```

Result:

**Accepted.**

This is the core proof that stable identities and frozen source symbols solve ordinary rename compatibility.

---

# 21. Mutation scenario 2 — add a hook to an existing populated resource

Existing application:

```text
Customer
├── 50,000 persisted rows
└── no custom extension
```

User enables:

```text
After Create hook
```

Forge generates or enables compiler-owned extension wiring.

If no user implementation exists, Forge offers:

> Create extension file

and writes once:

```text
internal/extensions/customer/hooks.go
```

with a no-op implementation.

No schema change is necessary merely to add an application lifecycle hook.

Existing data is unaffected.

Candidate build must compile before the spec revision becomes current.

Result:

**Accepted if compile succeeds.**

---

# 22. Mutation scenario 3 — drop a resource depended on by a relationship or hook

Initial:

```text
Customer
    ▲
    │ belongs_to
Project
```

plus:

```text
internal/extensions/customer/hooks.go
```

User attempts:

```text
Delete Customer
```

Forge detects:

1. `Project.Customer` depends on Customer.
2. Customer has active extension registration.
3. Deletion implies destructive database migration.

The initial transition is rejected.

UI reports:

> Customer cannot currently be deleted.
>
> Dependencies:
>
> * Project.customer relationship
> * Customer lifecycle extension
> * customer table contains persisted data

The user must resolve relationships and extension registration explicitly before deletion can proceed.

Even after dependencies are resolved, migration policy may require destructive-change confirmation.

Result:

**Rejected until dependencies and destructive intent are explicitly resolved.**

No invalid intermediate spec revision is committed.

---

# 23. Mutation scenario 4A — relabel without code refactor

Initial:

```text
Label:     Customer
Code name: Customer
```

User chooses:

```text
Rename display name → Client
```

Result:

```text
Label:     Client
Code name: Customer
```

Extensions remain valid:

```go
customer.CustomerView
```

Result:

**Accepted. ABI-neutral.**

---

# 24. Mutation scenario 4B — true code rename

Current:

```text
Label:     Client
Code name: Customer
```

User explicitly chooses:

```text
Refactor code identifier
Customer → Client
```

Forge classifies the change as ABI-breaking.

Candidate generation changes:

```go
CustomerView
```

to:

```go
ClientView
```

Existing extension:

```go
func (...) AfterCreate(... customer.CustomerView)
```

fails candidate compilation.

Forge rejects the transition and identifies the affected extension.

Only once extension code is manually updated in the candidate-compatible form may the refactor be committed.

Result:

**Explicit breaking refactor with compile gate.**

---

# 25. Field type changes

Type changes deserve ABI classification independently of naming.

Example:

```text
int → string
```

for a field with stable accessor:

```go
Quantity() int
```

would imply:

```go
Quantity() string
```

This is ABI-breaking.

Forge must:

1. classify the persistence migration;
2. classify the extension ABI change;
3. candidate-generate;
4. compile extensions;
5. reject if incompatible.

A stable ID does not mean a stable type.

---

# 26. Relationship changes

Relationships also receive stable IDs.

Example:

```json
{
  "id": "rel_01K...",
  "from": "project",
  "field_id": "fld_customer",
  "to": "customer",
  "kind": "belongs_to"
}
```

Changing:

```text
belongs_to Customer
```

into an unrelated target or different cardinality is not treated as a rename.

Forge must evaluate:

* source ABI;
* persistence migration;
* page references;
* admin metadata;
* extension API.

---

# 27. Frontend extensions

The same ownership principles apply to React/TypeScript.

Compiler-owned:

```text
frontend/src/forge_generated/
```

User-owned:

```text
frontend/src/extensions/
```

The first Forge MVP may expose fewer frontend extension points than backend hooks.

Do not invent a generic component/plugin runtime during F0.

The ABI rule remains identical:

> User frontend code may consume only explicitly supported generated contracts.

---

# 28. No partial file ownership

Rejected design:

```go
// FORGE:BEGIN
generated code
// FORGE:END

user code

// FORGE:BEGIN
more generated code
// FORGE:END
```

Forge will not maintain mixed-ownership source files.

Reasons:

* merge fragility;
* accidental marker deletion;
* formatting interactions;
* refactor ambiguity;
* poor Git diffs;
* generator complexity.

File ownership is directory/file-level, not region-level.

---

# 29. No AST rewriting of extension files

Gombit's generators legitimately use `go/ast` to make controlled edits to generated/application scaffolding.

Forge must **not** use AST rewriting as an excuse to modify user extension implementations.

The extension ABI is intended to eliminate that requirement.

If a breaking change requires updating user code, Forge reports it and the user performs the change.

---

# 30. Generated-code implementation freedom

Because extensions bind only to the supported ABI, Forge retains freedom to change generated internals.

For example:

```text
GORM storage implementation
handler layout
route helper structure
validation plumbing
admin wiring
```

may change between compiler versions without requiring extension modifications, provided the supported extension contract remains compatible.

This encapsulation is the main reason to avoid binding hooks directly to raw generated internals.

---

# 31. Extension ABI version

The generated extension surface carries an explicit ABI version.

Example:

```go
const ForgeExtensionABIVersion = 1
```

and/or project metadata:

```json
{
  "forge": {
    "spec_version": 1,
    "extension_abi_version": 1
  }
}
```

A major extension-ABI revision must be treated separately from ordinary compiler implementation changes.

---

# 32. Compiler compatibility

Forge compiler version and extension ABI version are distinct.

Example:

```text
Forge compiler:      0.7.3
ProjectSpec version: 2
Extension ABI:       1
Gombit protocol:     1
```

This allows compiler internals to evolve without falsely declaring every release an extension-breaking event.

---

# 33. Gombit boundary

Forge should not directly import unstable internal Gombit generator packages as its primary integration mechanism.

Forge sends one coarse-grained machine-readable project-generation request to a versioned Gombit interface.

Conceptually:

```text
Forge
  │
  │ one structured request
  ▼
gombit generate --machine
  │
  ▼
generated Gombit application
```

The command name is not locked by this ADR.

The architectural requirement is:

* versioned protocol;
* structured JSON input/output;
* one project-level invocation rather than N resource-level invocations;
* pinned Gombit version;
* no parsing of human-oriented CLI output.

---

# 34. Project serialization implications

Stable IDs must be preserved in the on-disk project specification.

The serialization must also be friendly to Git.

Requirements:

* deterministic ordering;
* sorted maps where applicable;
* stable arrays;
* no random reorder on save;
* IDs remain visible;
* formatting is deterministic.

Example:

```json
{
  "resources": [
    {
      "id": "res_A",
      "code_name": "Customer",
      "label": "Customer"
    },
    {
      "id": "res_B",
      "code_name": "Project",
      "label": "Project"
    }
  ]
}
```

Forge must not serialize semantically identical specs differently merely because of in-memory map iteration.

---

# 35. Interaction with Design Preview

Design Preview operates from `ProjectSpec`.

It does not execute backend extension code.

Therefore a resource with:

```text
AfterCreate hook
```

may display correctly structurally while its runtime behavior is absent.

Forge must label this explicitly.

Example:

> **Design Preview**
>
> Custom hooks are not executed here. Use Runtime Preview to test application behavior.

Likewise permission-dependent views may display a fidelity warning.

---

# 36. Interaction with Runtime Preview

Runtime Preview is the compatibility truth.

It uses:

```text
ProjectSpec
    ↓
Forge compiler
    ↓
Gombit generation
    ↓
user extensions
    ↓
compile
    ↓
real application
```

Runtime Preview executes:

* generated handlers;
* migrations;
* auth;
* permissions;
* user hooks;
* real database behavior.

---

# 37. Local toolchain consequence

This ADR does not choose the packaging strategy for Go/Node/Gombit on the user's machine.

However, it establishes one requirement:

> Extension compatibility cannot be considered fully validated without an actual compile/typecheck operation.

Therefore local Runtime Preview and ABI-breaking mutations require access to a functioning build toolchain.

Toolchain provisioning is handled by a separate ADR.

Design Preview must remain usable independently of that toolchain.

---

# 38. Interaction with migration intent

Stable IDs provide migration intent.

Example:

```text
same field ID
old DB name: email
new DB name: contact_email
```

means:

```text
rename_column
```

not:

```text
drop_column
add_column
```

The extension ABI and migration model therefore share the same identity foundation.

This ADR does not define the migration manifest format.

That belongs in the Gombit-level Migration Intent & Safety Manifest contract.

---

# 39. Compile gate policy

Forge may perform different levels of checking depending on mutation class.

### ABI-neutral change

Fast validation may be sufficient.

### Potential ABI-breaking change

Full generated backend compile is mandatory.

### Frontend contract change

TypeScript typecheck is mandatory when user frontend extensions consume the affected contract.

Forge must err toward refusing an unsafe transition rather than committing an internally inconsistent revision.

---

# 40. Atomic spec transitions

Complex edits should be represented as transactions over the candidate specification.

For example, removing:

```text
Customer
```

and simultaneously removing:

```text
Project.customer
```

should be validated as one candidate state.

Forge must not require every intermediate UI click to represent a valid persistent revision.

Conceptually:

```text
current valid state
       ↓
editing transaction
       ↓
candidate state
       ↓
validate
       ↓
next valid state
```

This avoids impossible workflows where users cannot remove mutually dependent pieces because the first deletion alone would be invalid.

---

# 41. User-owned code discovery

Forge may scan known extension directories to:

* determine whether extension files exist;
* include them in candidate builds;
* map compiler errors to extension files;
* detect orphaned extension directories.

Forge does not semantically parse these files to reconstruct application intent.

The source of truth remains `ProjectSpec`.

---

# 42. What Forge knows about extension code

Forge knows:

```text
where it is
which generated ABI it compiles against
whether it compiles
which resource/hook registration it belongs to
```

Forge does **not** attempt to know:

```text
what arbitrary business logic it implements
which external systems it calls
what semantic effect it has
how to translate it back into ProjectSpec
```

This boundary is permanent.

---

# 43. What happens after export

Export does not destroy the stable identity metadata.

The exported repository may retain:

```text
forge.json
```

and stable IDs for auditability and possible future tooling.

But Forge makes no round-trip guarantee once arbitrary external edits occur.

An exported application is ordinary source code.

---

# 44. Rejected alternatives

## A. Pure generation with mandatory eject for custom code

Rejected because the first unsupported behavior permanently ends Forge management.

---

## B. Arbitrary source editing with bidirectional reconciliation

Rejected as technically intractable for the product scope.

---

## C. Mixed generated/user regions in the same files

Rejected due to ownership ambiguity and generator fragility.

---

## D. Automatic symbol renames whenever labels change

Rejected because harmless visual changes would routinely break extension code.

---

## E. Expose raw GORM models as the permanent extension ABI

Rejected because persistence implementation details become a public compatibility contract.

---

## F. Runtime plugin/reflection system

Rejected for F0.

Forge extensions should remain ordinary statically compiled Go code.

---

# 45. Consequences

## Positive

* Visual renames usually do not break custom code.
* Forge can continue regenerating projects containing user extensions.
* Stable IDs power both source compatibility and migration intent.
* Compiler-owned/user-owned boundaries are obvious.
* Exported code remains ordinary Go.
* User extensions are statically type checked.
* No bidirectional source reconstruction is necessary.
* Generated internals retain substantial freedom to evolve.

---

## Negative

* Exported code may retain historical creation-time identifiers.
* Explicit code-symbol refactoring is more involved.
* Candidate spec transitions sometimes require a full compilation.
* Forge must maintain a versioned extension ABI.
* User code can still become incompatible with genuine semantic/type changes.
* Local Runtime Preview requires a working toolchain.
* Forge must provide high-quality compatibility diagnostics rather than generic compiler failures.

These costs are accepted.

---

# 46. F0 acceptance scenarios

F0 is not complete merely when it generates an application.

The following four scenarios must pass.

## Scenario A — harmless rename

Given:

```text
Customer.Email
```

used by a hook,

when the field is visually renamed and its database column is renamed,

then:

* stable ID remains;
* code accessor remains;
* hook remains unchanged;
* candidate app compiles;
* migration intent is rename rather than drop/add.

---

## Scenario B — extension added after data exists

Given a populated resource,

when an `AfterCreate` hook is enabled,

then:

* Forge adds the generated extension contract;
* Forge may create a no-op user file once;
* existing data is untouched;
* candidate app compiles;
* subsequent regeneration never rewrites the implementation file.

---

## Scenario C — dependency-breaking deletion

Given:

```text
Project → Customer
```

and Customer extension code,

when Customer is deleted,

then Forge rejects the candidate until:

* dependent relationships are resolved;
* active extension registration is resolved;
* destructive migration intent is explicitly acknowledged.

No invalid revision becomes current.

---

## Scenario D — relabel versus source refactor

Given:

```text
Customer
```

when the display label changes to:

```text
Client
```

then extensions continue compiling against the frozen `Customer` source API.

When the user separately requests:

```text
Customer → Client
```

as a code identifier refactor,

Forge classifies it as breaking and refuses to commit it while incompatible extension code remains.

---

# 47. F0 exit gate

ADR-001 is considered validated when a minimal hand-built/compiler-spike implementation proves:

```text
ProjectSpec
   │
   ├── stable resource IDs
   ├── stable field IDs
   ├── frozen source identifiers
   │
   ▼
generated application
   │
   ├── compiler-owned tree
   └── user-owned extension tree
             │
             ▼
       candidate compile
```

and all four mutation scenarios above behave as specified.

If the implementation requires Forge to rewrite arbitrary user extension code to make those scenarios work, this ADR has failed and must be revisited before the visual editor is built.

---

# 48. Locked architectural rule

The final rule is:

> **Forge owns structure; the developer owns behavior behind explicit seams. Stable identity connects the two, and Forge never silently turns a presentation change into a source-code breaking change.**

Everything in the Forge compiler and editor must preserve that boundary.
